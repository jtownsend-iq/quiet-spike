# SPIKE-01 — iOS scenarios A & B (2026-05-06)

**Verdict: PASS.** `t_keystroke` and `t_local` are 23–100× under their
respective SPIKE-01 budgets across both the foreground and the
force-quit-between-each cold-start path on the test device.

brackets that gate it. The remaining brackets (`t_e2e`, `t_converge`)

## What this proves and doesn't prove

**Proves:**

1. SwiftUI's TextField + first-frame render after first keystroke
   is nowhere near the perceptual budget on an iPhone 14. P95 is
   12 ms — well below the 16.7 ms vsync interval, meaning the first
   frame after typing usually lands on the *very next* refresh.
2. GRDB's `write{}` block — wrapping a single-row INSERT in a
   transaction with `synchronous=FULL` (i.e., real fsync to APFS) —
   completes in ~18 ms median. The "field clears on commit" receipt
   is honest: the row is durable on disk before the field clears.
3. Cold start does **not** degrade either bracket on iOS 26.3.1 /
   iPhone 14. App launch + scene init + GRDB DatabaseQueue creation
   is fast enough that the first capture after force-quit is
   indistinguishable from a foreground capture in the data.
4. The latency-harness JSONL shape from `LatencyLog.swift` matches
   `spike/analyze.py` and the synthetic fixture verifier exactly
   (proven by running `analyze.py --strict` against the device log
   and getting valid percentile output, no schema warnings).

**Does not prove:**

1. `t_e2e` budget (≤3 s P50 / ≤6 s P95). Not measured — PowerSync
   wiring is deferred to next session.
2. `t_converge` budget (≤2 s when both online). Not measured — needs
   a second device, which session 4 sets up.
3. Steady-state behaviour over 200 captures. n=20–45 is enough to
   call the budget but not enough to characterise the long-tail
   shape (P99 / outliers under sustained typing).
4. iOS device floor — the iPhone 14 (A15) is one generation newer
   than the iPhone 13 the spike doc names as the iOS floor. P50 of
   10 ms / 18 ms gives plenty of room for an iPhone 13 to land
   somewhere near 12 ms / 22 ms and still pass with 30× headroom,
   but a real iPhone 13 measurement before the production launch
   would close that gap.
5. Anything about the share extension, Siri intent, or post-call
   surfaces — those are micro-spikes per SPIKE-01 § "What the spike
   deliberately does not prove" and run only after the in-app sheet
   is green. The in-app sheet is now green. Those micro-spikes are
   unblocked.

## Bottleneck analysis (precautionary)

The numbers are far enough under budget that there's no bottleneck
to name. For completeness, the highest-cost segment in `t_local` is
the GRDB `write{}` closure (~18 ms median). That cost is dominated by
the APFS fsync itself, not GRDB's overhead — Swift method dispatch
and SQLite parsing are at most a few hundred microseconds. This means
the budget is essentially set by Apple silicon's NAND + APFS, which
is a comfortable place to be.

If a future regression appears (say, `t_local` P95 climbs above
50 ms), suspect order-of-operations:

1. Did journal mode change? WAL would *lower* the cost; default
   should be the slowest path.
2. Did the schema add a new index? Each index gets fsync'd in the
   same transaction.
3. Did some upstream code wrap commit in a background queue without
   `Dispatch.sync`? — that would add a vsync of latency for the
   field-clear paint.
